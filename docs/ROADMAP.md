# ShuggaBuddy — Roadmap

## О продукте

ShuggaBuddy — Telegram-бот, карманный помощник по самоконтролю для людей с
диабетом 1 типа на базально-болюсной инсулинотерапии. Бот снижает когнитивную
нагрузку пациента: ведёт дневник самоконтроля, рассчитывает дозы инсулина,
импортирует данные с систем непрерывного мониторинга глюкозы (CGM), выявляет
паттерны в показателях и предупреждает о рисках.

**Бот не заменяет врача.** Все рекомендации по дозированию сопровождаются
дисклеймером о необходимости врачебной консультации; решение о дозе инсулина
всегда принимает пользователь.

**Аудитория:** люди с СД1 на базально-болюсной терапии; пользователи CGM
(FreeStyle Libre, Dexcom и др.); родители детей с СД1.

**Принципы:** простота записи событий, персонализация под индивидуальные
коэффициенты, прозрачность расчётов (бот объясняет логику), безопасность.

**Стек:** Go 1.25, PostgreSQL 14+, Clean Architecture
(domain / usecase / repository / delivery), goose-миграции, фоновые schedulers,
Telegram Bot API (`go-telegram-bot-api`), Zap-логирование.

## Как читать

- `[x]` — сделано, `[ ]` — не сделано, 🟡 — частично.
- Каждая невыполненная задача оформлена как **user story** + **критерии приёмки**
  (вложенные чекбоксы — отмечай по мере реализации).
- Каждая задача атомарна: один разработчик закрывает её максимум за неделю.
- Роли в историях: **П** — пользователь с СД1, **Р** — родитель ребёнка с СД1,
  **сис** — система/бот.

### Приоритеты

- **P0 — критично:** безопасность пациента, потеря или искажение данных, стабильность.
- **P1 — высокий:** базовая ценность дневника и расчётов, чего пользователи ждут в первую очередь.
- **P2 — средний:** повышение точности и удобства.
- **P3 — низкий:** продвинутые возможности, LLM-расширения, задел на будущее.

Рекомендуемый порядок реализации — в разделе [Приоритетные волны](#приоритетные-волны) внизу.

## Этап 0 — Фундамент

- [x] Telegram-бот на `go-telegram-bot-api`, цикл обработки апдейтов
- [x] PostgreSQL + goose-миграции (16 миграций)
- [x] Clean Architecture (domain / usecase / repository / delivery)
- [x] Команда `/start`, регистрация пользователя, главное меню (inline-кнопки)
- [x] Ручной ввод и сохранение уровня глюкозы

- [x] CI/CD через GitHub Actions (lint, test, e2e)
- [x] Zap-логирование, конфиг через `.env`

- [ ] **Persistent-сессии** · P1
  - **Story:** Как П, я хочу, чтобы начатый ввод (например, доза инсулина) не
    терялся при перезапуске бота, чтобы не вводить данные заново.
  - **Критерии приёмки:**
    - [ ] Состояние сессии (step + data) хранится вне памяти процесса (БД или Redis)
    - [ ] После рестарта бота незавершённый ввод восстанавливается на том же шаге
    - [ ] У сессии есть TTL: брошенный ввод истекает через N минут
    - [ ] Покрыто тестом: сохранение → «рестарт» (новый инстанс) → продолжение шага

- [ ] **Sentry / структурированный error-tracking** · P1
  - **Story:** Как разработчик, я хочу видеть паники и ошибки прода с контекстом,
    чтобы чинить проблемы до жалоб пользователей.
  - **Критерии приёмки:**
    - [ ] Все паники в хэндлерах и schedulers перехватываются и репортятся, бот не падает
    - [ ] В событие попадают user_id, тип апдейта, текст ошибки (без чувствительных данных)
    - [ ] DSN читается из конфига; при пустом DSN репортинг тихо отключён
    - [ ] PII (токены CGM, пароли) не утекают в события

## Этап 1 — Дневник самоконтроля

- [x] Запись глюкозы: валидация, конвертация единиц, индикатор диапазона 🔴🟢🟡
- [x] Запись еды: углеводы в г / ХЕ, переключение единиц, заметка, выбор времени
- [x] Запись инсулина: болюс/базальный, валидация дозы, аномальные дозы, препарат
- [x] Запись активности: тип, длительность, интенсивность, риск, окно мониторинга
- [x] Корреляция активности с глюкозой (delta до/после)
- [x] Заметки: самочувствие, болезнь, стресс, свободный текст
- [x] Дневник: фид за день, навигация по датам, ввод даты вручную

- [ ] **Редактирование/удаление записи** · P1
  - **Story:** Как П, я хочу поправить или удалить ошибочную запись, чтобы дневник
    и расчёты (болюс, advisor) опирались на корректные данные.
  - *Влияет на безопасность: ошибочные данные искажают расчёт доз.*
  - **Критерии приёмки:**
    - [ ] Из фида можно открыть запись и нажать «Изменить» или «Удалить»
    - [ ] Редактирование переиспользует валидацию соответствующего usecase
    - [ ] Удаление запрашивает подтверждение
    - [ ] Изменённые/удалённые записи сразу обновляются в фиде и в выборках для
          калькулятора и advisor
    - [ ] Тесты usecase на update/delete + проверка прав (нельзя тронуть чужую запись)

- [ ] **Поиск/фильтр по дневнику** · P2
  - **Story:** Как П, я хочу отфильтровать фид дня по типу записи (только глюкоза,
    только еда…), чтобы быстро найти нужное в насыщенном дне.
  - **Критерии приёмки:**
    - [ ] В дневнике есть кнопки-фильтры: Все / Глюкоза / Еда / Инсулин / Активность / Заметки
    - [ ] Активный фильтр визуально выделен и сохраняется при переходе между днями
    - [ ] При пустом результате — понятное сообщение «нет записей этого типа за день»
    - [ ] Навигация по датам работает с учётом активного фильтра

- [ ] **Быстрый повтор частых вводов** · P2
  - **Story:** Как П, я хочу вводить частые дозы и продукты в один тап, чтобы
    тратить на запись секунды, а не минуту.
  - **Критерии приёмки:**
    - [ ] Бот предлагает 3–5 наиболее частых доз инсулина за последние 30 дней
    - [ ] Бот предлагает 3–5 наиболее частых записей еды (граммы/ХЕ + заметка)
    - [ ] Тап по пресету сразу переходит к подтверждению/времени, минуя ручной ввод
    - [ ] Список пресетов перестраивается по мере накопления истории

## Этап 2 — Калькулятор болюса

- [x] Болюс на еду по ICR из истории (14 дней), коррекция по ISF, учёт IOB
- [x] Итоговая доза с пошаговым объяснением, сохранение как инъекции
- [x] Каталог 8 болюсных препаратов с параметрами DIA

- [ ] **Ручная настройка ICR/ISF в профиле** · P1
  - **Story:** Как новый П без накопленной истории, я хочу задать свои ИЧ и ФЧИ
    вручную, чтобы калькулятор работал с первого дня.
  - **Критерии приёмки:**
    - [ ] В профиле можно ввести ICR (г/ед.) и ISF (ммоль/л на ед.) с валидацией границ
    - [ ] Калькулятор использует ручные значения, если они заданы
    - [ ] Если ручных нет — fallback на вывод из истории (текущее поведение)
    - [ ] В объяснении расчёта указан источник коэффициентов: «задан вручную» / «по истории»
    - [ ] Миграция добавляет поля; тесты на приоритет ручных значений

- [ ] **ICR/ISF по времени суток** · P2
  - **Story:** Как П, у которого утром инсулинорезистентность выше, я хочу разные
    коэффициенты для утра/дня/вечера, чтобы расчёт был точным в любое время.
  - **Критерии приёмки:**
    - [ ] Профиль хранит несколько временных блоков (утро/день/вечер/ночь) с ICR/ISF
    - [ ] Калькулятор выбирает блок по времени приёма пищи (в таймзоне пользователя)
    - [ ] UI настройки позволяет задать границы блоков и значения
    - [ ] В объяснении показан использованный временной блок
    - [ ] Тесты на выбор блока по граничным временам (00:00, переход через полночь)

- [ ] **Поправка болюса на физнагрузку** · P2
  - **Story:** Как П, который недавно тренировался, я хочу, чтобы калькулятор
    предложил сниженную дозу, чтобы избежать отложенной гипогликемии.
  - **Критерии приёмки:**
    - [ ] При активности с риском Moderate/High в окне последних N часов доза
          снижается на настраиваемый % с пометкой в объяснении
    - [ ] Размер поправки зависит от уровня риска активности
    - [ ] Поправку можно отключить в настройках
    - [ ] Тесты: с активностью / без активности / разные уровни риска

- [ ] **Нелинейная модель IOB** · P3
  - **Story:** Как П на современном аналоге инсулина, я хочу, чтобы IOB считался по
    кривой действия с пиком, чтобы остаток инсулина оценивался точнее.
  - **Критерии приёмки:**
    - [ ] IOB рассчитывается по кривой с использованием PeakMin/PeakMax препарата
    - [ ] При недоступных параметрах пика — fallback на текущую линейную модель
    - [ ] Юнит-тесты сверяют значения IOB с эталонными точками кривой
    - [ ] Объяснение расчёта не регрессирует (модель прозрачна для пользователя)

## Этап 3 — Профиль и персонализация

- [x] Просмотр профиля, единицы mmol/L ↔ mg/dL, целевой диапазон
- [x] Граммы на 1 ХЕ, базальный инсулин (препарат + время)
- [x] Часовой пояс (12 пресетов), болюсный препарат
- [x] Доза базального + интервал автоуведомлений advisor

- [ ] **Онбординг-тур** · P1
  - **Story:** Как новый П, я хочу за пару минут после `/start` настроить ключевые
    параметры, чтобы сразу пользоваться ботом без поиска по меню.
  - **Критерии приёмки:**
    - [ ] После первого `/start` запускается последовательность: единицы → целевой
          диапазон → базальный → (опц.) болюсный → (опц.) CGM
    - [ ] Любой шаг можно пропустить и вернуться к нему позже из профиля
    - [ ] Прогресс онбординга сохраняется; повторный `/start` не запускает тур заново
    - [ ] По завершении — короткая подсказка по главному меню
    - [ ] Тест проходит полный happy-path онбординга

- [ ] **Произвольный часовой пояс** · P3
  - **Story:** Как П вне России, я хочу указать свой IANA-таймзон, чтобы расчёты
    «натощак» и время записей были корректны.
  - **Критерии приёмки:**
    - [ ] Можно ввести валидный IANA TZ (например, `Europe/Berlin`) помимо 12 пресетов
    - [ ] Невалидный ввод отклоняется с понятной ошибкой
    - [ ] Введённая таймзона применяется во всех временных расчётах (advisor, дневник)

- [ ] **Алерты гипо/гипергликемии** · P0
  - **Story:** Как П (или Р), я хочу получать пуш в Telegram при выходе глюкозы за
    пороги, чтобы вовремя среагировать на гипо/гипергликемию.
  - **Критерии приёмки:**
    - [ ] Пороги гипо/гипер настраиваются в профиле (дефолт < 3.9 / > 10.0 ммоль/л)
    - [ ] `cgm_sync` scheduler при новом значении за порогом шлёт уведомление
    - [ ] Текст алерта содержит значение, тренд-стрелку и время
    - [ ] Алерты можно включить/выключить отдельно от синхронизации
    - [ ] Тесты: значение ниже / в диапазоне / выше → отправка/молчание

- [ ] **Антидребезг алертов** · P1
  - **Story:** Как П в затяжной гипогликемии, я не хочу получать один и тот же алерт
    каждые 5 минут, чтобы уведомления не превращались в спам.
  - **Критерии приёмки:**
    - [ ] Повторный алерт того же типа не шлётся чаще, чем раз в N минут (настраиваемо)
    - [ ] При возврате в диапазон и новом выходе за порог алерт приходит снова
    - [ ] Состояние «последний алерт» переживает перезапуск бота
    - [ ] Тесты на окно подавления и на сброс после нормализации

- [ ] **TIR (Time in Range)** · P1
  - **Story:** Как П, я хочу видеть % времени в целевом диапазоне за день/неделю,
    чтобы оценивать качество компенсации.
  - **Критерии приёмки:**
    - [ ] Расчёт % времени ниже / в диапазоне / выше за выбранный период
    - [ ] Используются как CGM-, так и ручные показания в окне
    - [ ] Результат показан карточкой с разбивкой и числом замеров
    - [ ] Корректная обработка периода без данных
    - [ ] Юнит-тесты на расчёт долей по набору показаний

- [ ] **График глюкозы в чате** · P2
  - **Story:** Как П, я хочу посмотреть график за 8–24 часа прямо в чате, чтобы
    оценить динамику без сторонних приложений.
  - **Критерии приёмки:**
    - [ ] Бот отправляет изображение графика глюкозы за выбранный интервал
    - [ ] На графике видны целевой диапазон и точки замеров
    - [ ] MVP-вариант (ASCII-спарклайн) допустим, если рендер PNG откладывается
    - [ ] Понятное сообщение, если данных за период нет

  - **Story:** Как П, я хочу раз в неделю получать сводку, чтобы отслеживать

    - [ ] Пользователям без данных дайджест не отправляется
    - [ ] Тест на формирование дайджеста и на условие отправки

- [ ] **Выявление паттернов (rule-based)** · P2
  - **Story:** Как П, я хочу узнавать о повторяющихся гипо/гипер в одно и то же

  - **Критерии приёмки:**
    - [ ] Анализ группирует выходы за диапазон по времени суток за 7–14 дней
    - [ ] Паттерн фиксируется при повторении ≥ заданного числа раз
    - [ ] Вывод текстом с временным окном и направлением (гипо/гипер) + дисклеймер
    - [ ] Юнит-тесты на детекцию и на отсутствие ложных паттернов

- [ ] **Экспорт в PDF** · P2
  - **Story:** Как П, я хочу выгрузить аккуратный отчёт в PDF, чтобы передать

  - **Критерии приёмки:**
    - [ ] PDF включает сводку (среднее, TIR, GMI) и таблицу записей за период

    - [ ] Зависит от готовности агрегатов (TIR, GMI, суточный отчёт)

- [ ] **Анализ влияния продуктов** · P3
  - **Story:** Как П, я хочу видеть, как конкретная еда влияет на сахар через 2 часа,

  - **Критерии приёмки:**
    - [ ] Для записей еды считается постпрандиальная дельта глюкозы (через ~2 ч)
    - [ ] Результаты группируются по заметке/продукту с усреднением
    - [ ] Корректная обработка случаев без замера после еды
    - [ ] Юнит-тесты на сопоставление еда↔постпрандиальная глюкоза
